### 三、简答题（6 题 × 2 分）

**1. 为什么索引用 B+ 树，不用 B 树、哈希、红黑树？**
> 答：B+树非叶子节点只存‘索引值加主键’，叶子节点存数据，非叶只存键，扇出大，IO次数少并稳定，层级>     次数少3层存千万级
>

**2. 什么是回表？有哪些避免回表的手段？**
> 答：在二级查询中查询到索引值再返回主表按主键再查一次聚簇索引找出数据的过程叫回表。把常用列设索引，与主键等关联。走联合索引或覆盖索引
>
>

**3. 联合索引 `(a,b,c)` 为什么 `where b=1` 用不上索引？**
> 答：最左前缀不满足，无法二分定位，直接退化为条件查询
>
>

**4. 写出至少 5 种索引失效场景，每种给一句改写方案。**
> 答：n1列上运算：id +1 =2 -----> id =1
>	    n2列上函数：date(time)  -----> time>=…… and time<……
>	    n3隐式转换：phone = 13924460417 ----->  phone =‘13924460417’
>   	n4前导模糊：name = ‘%张’-----> name = ‘张%’或改业务
>	    n5跳最左列：where b = 1 -----> 补a的值或单建b索引
>	    n6范围后失效： where a>1 and b =2 -----> 把等值放前面
>    	n7 ：or连裸列 ----- > 拆union
>     n8 :优化器估算回表太多主动放弃 → force index 验证（慎用到生产）
>
>

**5. 深分页为什么慢？两种优化写法各有什么限制？**
> 答：要不断扫描并回表直到开始索引，量级呈倍数上涨。
>       书签：不可跳页，只可下一页
>       延迟关联：要join临时表关联
>
>

**6. `update` 的行锁加在什么地方？有索引和无索引差在哪？**
> 答：加在索引项上，有索引在扫描时不用锁全表，只锁命中的行，无索引则要锁全表
>
>

## 7. 面试三问口述（碎片时间做，吃饭/走路都行）

W1 的自查 3 问，要求**每问连续讲 60 秒以上**，卡壳就是没掌握。

**第 1 问：为什么用 B+ 树？**（骨架）
> 结论句：因为要「矮、扇出大、范围友好」。→ 四点：3 层存千万级；非叶子只存键所以扇出大；叶子有序且链表相连，范围查询和排序不用回表；每次查询磁盘 IO 次数稳定。→ 对比：哈希只支持等值、红黑树层数太高每层一次 IO、B 树非叶子也存数据导致扇出小。

**第 2 问：什么是回表？**（骨架）
> 定义：二级索引叶子只存主键，要拿其它列就得再按主键查一次聚簇索引。→ 代价：多一次 B+ 树查找（可能多几次 IO）。→ 避免：覆盖索引（把要查的列放进索引）、尽量只查索引列、联合索引设计时把高频查询列带上。

**第 3 问：5 种索引失效 + 改写？**（骨架）
> 列运算 → 改成范围；列函数 → 改写成范围或加函数索引；隐式转换 → 类型对齐（字符串加引号）；前导 `%` → 改成后缀匹配或全文/搜索引擎；跳最左列 → 补上最左列或建新索引。

### 一、判断题

1. **❌ 错**。最小 IO 单位是**页（16KB）**，行是逻辑单位；读一行也要把整页读进来。
2. **❌ 错**。MyISAM 只有**表锁**、不支持事务；小表全表扫描确实快，但原因是数据文件小，不是"支持行锁"。
3. **✅ 对**。聚簇索引叶子节点就是数据页，存整行。
4. **✅ 对**。二级索引叶子存「索引列 + 主键」，查其它列要回表。
5. **❌ 错**。B+ 树按 `(a,b,c)` 排序，跳过 `a` 就无法定位，`type` 会退化成 `ALL`（除非能走覆盖索引的 index 扫描）。
6. **✅ 对**（严格说：不能用于**定位**，只能全索引扫描）。前导 `%` 破坏了前缀有序性。
7. **❌ 错**。优化器会挑**最小的二级索引**扫，只读索引项，不读整行；真正慢的是 `count(可空列)`。
8. **✅ 对**。没有索引只能全表扫描，扫描到的行全部加锁（RR 下含间隙锁），表现为锁全表。

### 二、选择题

1. **C** 16KB。
2. **B** 64（1MB ÷ 16KB = 64）。
3. **C**。A 列上有函数；B 隐式转换（varchar 列和数字比较，列被转成数字）；D 列上运算。C 是后缀匹配，能定位前缀。
4. **B**。判定标准只有一个：查询涉及的所有列都在索引里 → `Extra: Using index`。
5. **A**。`where age=20` 是等值，`(age,city)` 在 `age` 相同时 `city` 有序，顺序一致所以不需要 filesort。
6. **B**。延迟关联（子查询取 id 再 join）或书签（`id > last_id`）。
7. **B**。是统计信息里的**估算值**，误差可能很大，只能用来"大概知道量级"。
8. **C** 10 秒（所以学习环境要手动调到 0.5～1 秒）。

### 三、简答题（要点，能说到这些就算对）

1. **B+ 树**：3 层存千万级、非叶子只存键扇出大、叶子有序且链表相连（范围/排序友好）、IO 次数稳定。**B 树**：非叶子也存数据，扇出小、树更高。**哈希**：只适合等值，范围/排序/最左前缀全废（InnoDB 的自适应哈希只做内部加速）。**红黑树**：二叉、层数太多，每层一次 IO，千万级要 20+ 层。
2. 回表：二级索引叶子只有「索引列 + 主键值」，查其它列时按主键再查一次聚簇索引，多一次 B+ 树查找。避免：①覆盖索引（查询列全在索引里）；②把高频查询列加进联合索引；③能用主键就别用二级索引。
3. 因为索引是按 `(a,b,c)` 顺序建的：先按 a 排、a 相同再按 b 排。不给 a 的值，b 在整个索引里是"乱序"的，无法二分定位。这就是最左前缀。
4. ①列上运算 `id+1=2` → `id = 1`；②列上函数 `date(t)=...` → 改范围 `t >= ... and t < ...`；③隐式转换 `phone = 138...` → `phone = '138...'`；④前导模糊 `like '%张'` → `like '张%'` 或改业务（全文索引/搜索引擎）；⑤跳最左列 `where b=1` → 补 `a` 或建 `(b)` 索引；⑥范围后失效 `a>1 and b=2`（b 用不上）→ 把等值列放前面；⑦`or` 连裸列 → 拆 `union`；⑧优化器估算回表太多主动放弃 → `force index` 验证（慎用到生产）。
5. 慢在"扫了再丢"：扫 `offset+n` 行、丢前 offset 行。①延迟关联：子查询走覆盖索引只取 id，再 join 回表 n 次——可跳页，但要求子查询的排序能走索引；②书签 `where id > last_id limit n`——代价最小，但不能跳页、要求排序键唯一有序。
6. 行锁加在**索引项**上，不是行上。有索引 → 只锁命中的行（RR 下普通索引还有间隙锁）；无索引 → 全表扫描 → 扫到的行全部加锁，表现为锁全表，极易阻塞和死锁。所以 update 的 where 列必须先建索引。

### 四、SQL 分析

1. 能走 `idx_user_status`（`user_id` 等值 + `status` 等值 → `type=ref`，`key_len` 两列都算）。`create_time` 的排序**用不上** `idx_create`，因为 `where` 已经选了 `idx_user_status`，排序字段不在该索引里 → 会 `Using filesort`。改法：①建 `idx_user_status_time(user_id, status, create_time)`，等值前缀 + 排序列同一索引 → 消除 filesort；②或业务层接受排序（数据量小）。
2. `key_len = 4 + 82 = 86`。计算：`a INT NOT NULL` = 4；`b VARCHAR(20) NOT NULL` utf8mb4 → 20 × 4 = 80，varchar 变长额外 +2 = 82，NOT NULL 不加 1；`c` 没用到不计。若 `b` 可空则 83，`c DATETIME` 可空用上是 5+1=6。
3. 延迟关联：`SELECT o.* FROM t_order o JOIN (SELECT id FROM t_order ORDER BY id LIMIT 500000, 20) x ON o.id = x.id;`（或书签：`SELECT * FROM t_order WHERE id > 500000 ORDER BY id LIMIT 20;`）

### 五条要补（按性价比排序，各 5 分钟）

1. **行 vs 页**：InnoDB 最小 IO 单位是页 16KB，行是逻辑单位 → `day1` §2。
2. **B+ 树四问对比**：B 树（非叶也存数据、扇出小）、哈希（只等值）、红黑树（层数高、每层一次 IO）→ `day2` 全文，最好背下三段式：结论 → 四优点 → 三对比。
3. **深分页「扫了再丢」**：一句话记住「limit 不是跳转，是数过去再丢」→ `day6` §1。
4. **RR 间隙锁**：有索引也未必只锁一行，普通索引在 RR 下是临键锁（记录 + 间隙）；这也解释了为什么「无索引锁全表」比「有索引」危险得多。
5. **术语精确化**：`type=ALL` / `like` / 「索引列值」这些词面试里会被追问，说错比不会更伤。
